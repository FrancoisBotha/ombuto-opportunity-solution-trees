# Test Strategy

This project was generated by **JHipster 9.0.0** (monolith, Maven, Vue 3, OAuth2/Keycloak,
spring-websocket, Cucumber) rather than scaffolded by Initiate Stack. JHipster ships a complete
test toolchain; this document records how to drive it. Every command below runs from the
repository root. On Windows use `./mvnw` from Git Bash or `mvnw.cmd` from PowerShell/cmd.

The backend flags `-Dskip.installnodenpm -Dskip.npm` appear on every Maven command on purpose:
they stop Maven from installing Node and rebuilding the webapp, which is never needed to run
Java tests.

## 1. Stack and frameworks

**Backend**

- Language and version: Java 21 (`<java.version>` in `pom.xml`; newer JDKs work — verified on 25), Spring Boot 4.0.3, Maven via wrapper (`./mvnw`)
- Test framework(s): JUnit 5 (Jupiter) + AssertJ + Mockito via `spring-boot-starter-test`; Spring `MockMvc` for REST; ArchUnit 1.4.1 (`TechnicalStructureTest`); Cucumber 7.34 on the JUnit Platform; Testcontainers PostgreSQL (`-Pprod` only)
- Lint tool(s): Checkstyle 13 with `checkstyle.xml` — **nohttp rule only** (flags `http://` URLs); Modernizer (legacy-API check, bound to `package`)
- Type-check tool(s): `javac` — the compile is the type check
- Code formatter(s): Prettier with `prettier-plugin-java` (`.prettierrc`, 4-space Java, 140 cols). Spotless is wired into `process-sources` but has no formatter steps configured — it is a no-op, Prettier is the real formatter.

**Frontend**

- Language and version: TypeScript + Vue 3, Node `>=24.14.0` (`package.json` engines), Vite
- Test framework(s): Vitest (`vitest.config.ts`, `happy-dom`, globals on) + `@vue/test-utils`, `@pinia/testing`, `sinon`, `axios-mock-adapter`
- Lint tool(s): ESLint flat config (`eslint.config.ts`) with `typescript-eslint` and `eslint-plugin-vue`
- Type-check tool(s): none — `vue-tsc` is not installed and `vite build` does not type-check. ESLint's TypeScript rules are the only static check.
- Code formatter(s): Prettier (`.prettierrc`, `.prettierignore`); also enforced on commit by husky + lint-staged

**End-to-end**

- Playwright (`playwright.config.ts`), Chromium only, logs in through Keycloak once and reuses the session.

## 2. Test directory layout

| What | Where |
|---|---|
| Java unit tests (`*Test.java`) | `src/test/java/com/opportunity/tree/**` — mirrors the main package |
| Java integration tests (`*IT.java`, full Spring context) | same tree, mostly `web/rest/`, `service/`, `security/`, `config/` |
| Integration-test meta-annotation | `src/test/java/com/opportunity/tree/IntegrationTest.java` (`@IntegrationTest`) |
| Entity test fixtures | `domain/*TestSamples.java`, `domain/*Asserts.java` |
| Architecture rules | `src/test/java/com/opportunity/tree/TechnicalStructureTest.java` |
| Cucumber runner + step defs | `src/test/java/com/opportunity/tree/cucumber/` (`CucumberTest`, `stepdefs/`) |
| Cucumber feature files | `src/test/resources/com/opportunity/tree/cucumber/*.feature` |
| Test Spring config | `src/test/resources/config/application.yml`, `application-testdev.yml` (H2), `application-testprod.yml` (Testcontainers PostgreSQL) |
| JUnit platform settings (timeouts, class order) | `src/test/resources/junit-platform.properties` |
| Frontend unit tests (`*.spec.ts`) | **co-located** with the source under `src/main/webapp/app/**` |
| Frontend test setup | `src/main/webapp/app/test-setup.ts` |
| Playwright E2E | `src/test/javascript/playwright/*.spec.ts`, `auth.setup.ts`, `support/` (excluded from Vitest) |

All generated output lands under `target/` (already git-ignored): `surefire-reports/`,
`failsafe-reports/`, `cucumber-reports/`, `site/jacoco*/`, `test-results/`, `vite-coverage/`,
`playwright/`.

## 3. How to run tests for a specific file or test class

**Java unit test (`*Test`) — Surefire, ~20 s**

```bash
./mvnw -ntp --batch-mode -Dskip.installnodenpm -Dskip.npm test -Dtest=TagTest
# one method:   -Dtest='TagTest#equalsVerifier'
# several:      -Dtest='TagTest,TagMapperTest'
```

**Java integration test (`*IT`) — Failsafe, ~35 s+ (boots Spring + H2)**

```bash
./mvnw -ntp --batch-mode -Dskip.installnodenpm -Dskip.npm verify \
  -Dtest=NoUnitTests -Dsurefire.failIfNoSpecifiedTests=false \
  -Dit.test=TagResourceIT
# one method:   -Dit.test='TagResourceIT#putExistingTag'
```

`-Dtest=NoUnitTests -Dsurefire.failIfNoSpecifiedTests=false` skips the unit-test pass so only
the named IT runs. `*IT` classes are **not** picked up by `./mvnw test` — they need `verify`.
**Cucumber features — ~1 min, requires Docker.** The runner is named `CucumberTest`, so it runs
under Surefire, and `CucumberTestContextConfiguration` hard-codes the `testprod` profile
(Testcontainers PostgreSQL). It therefore only passes with `-Pprod` and Docker running:

```bash
./mvnw -ntp --batch-mode -Dskip.installnodenpm -Dskip.npm test -Pprod -Dtest=CucumberTest
```

**Frontend spec — Vitest, ~10 s**

```bash
npx vitest run src/main/webapp/app/account/account.service.spec.ts
# by test name:  npx vitest run <file> -t "should init service"
```

On Node 25+ prefix with `NODE_OPTIONS=--no-experimental-webstorage` (see section 9).
Do **not** use `npm test -- <file>` for a single spec: `npm test` first lints the whole repo
(`pretest`), which currently hangs (section 9).

**Playwright spec** (requires the running stack — see section 8)

```bash
npx playwright test src/test/javascript/playwright/sidebar.spec.ts
```

## 4. How to run the full project test suite

```bash
# Backend: unit + Cucumber + integration tests + checkstyle + JaCoCo — REQUIRES DOCKER
npm run backend:unit:test -- -Pprod
#   = ./mvnw -ntp -Dskip.installnodenpm -Dskip.npm verify --batch-mode -Pprod  (logging silenced)
#   This is the same path JHipster's own `ci:backend:test` takes (default_environment = prod).

# Frontend: repo-wide ESLint, then all Vitest specs with coverage (~25 s total)
npx eslint . --ignore-pattern ".ombutocode/"
npx vitest --run --coverage
#   These two lines are what `npm test` does (pretest = lint, test = vitest), minus the
#   `.ombutocode/` crawl that makes the stock `npm test` / `npm run lint` hang — see section 9.
```

Both must pass for the regression closeout. There is no single command that runs both; run them
one after the other.

**Why `-Pprod`:** under the default `dev` profile `CucumberTest` always errors (it hard-codes
`testprod`, see section 9), Surefire fails, and Maven stops **before the `*IT` classes ever run** —
so a plain `npm run backend:unit:test` is red and tells you nothing about the integration tests.

**No Docker available?** Run everything except Cucumber on H2, and record Cucumber as skipped:

```bash
./mvnw -ntp --batch-mode -Dskip.installnodenpm -Dskip.npm verify \
  '-Dtest=!CucumberTest,!*IT,!*IntTest' -Dsurefire.failIfNoSpecifiedTests=false
```

The `!*IT,!*IntTest` parts are required: a user-supplied `-Dtest` **replaces** Surefire's
configured excludes, so `'-Dtest=!CucumberTest'` alone would run every `*IT` under Surefire
without the `testdev` profile and fail them all for the wrong reason.

Optional, heavier:

- `npm run e2e` — Playwright suite. Not part of the default regression run; see section 8.

## 5. Lint and type-check commands

| Check | Scoped to files | Whole repo |
|---|---|---|
| ESLint (`eslint.config.ts`) | `npx eslint <files>` | `npx eslint . --ignore-pattern ".ombutocode/"` (add `--fix` to auto-fix). Not `npm run lint` — it hangs, section 9 |
| Prettier (`.prettierrc`, `.prettierignore`) — covers `.java`, `.ts`, `.vue`, `.json`, `.yml`, `.md`, `.scss`, `.html` | `npx prettier --check <files>` / `--write <files>` | `npm run prettier:check` / `npm run prettier:format` |
| Java compile (type check) | not file-scopable | `./mvnw -ntp --batch-mode -Dskip.installnodenpm -Dskip.npm test-compile` |
| Checkstyle nohttp (`checkstyle.xml`) | not file-scopable | `npm run backend:nohttp:test` (= `./mvnw -ntp checkstyle:check`) |
| Javadoc validity | not file-scopable | `npm run backend:doc:test` |
| Frontend type check | none — `vue-tsc` not installed | none |

husky's pre-commit hook runs `lint-staged` → `prettier --write` on staged files
(`.lintstagedrc.cjs`), so a commit may reformat what was staged.

## 6. Coverage and reporting

- **Backend — JaCoCo**, produced automatically by `verify`. Reports: `target/site/jacoco/index.html`
  (unit) and `target/site/jacoco-it/index.html` (integration). No minimum threshold is enforced.
- **Frontend — Vitest v8 coverage**, produced by `npx vitest --run --coverage`. Report:
  `target/vite-coverage/`. `vitest.config.ts` lists targets of statements 85 %, lines 85 %,
  branches 75 %, but they are **not enforced**: they sit directly under `coverage` rather than
  `coverage.thresholds`, which Vitest 4 ignores. Baseline 2026-09-18: 73.7 % statements, 73.9 %
  branches, 76.8 % lines, exit code 0. Treat the numbers as a target, not a gate — new components
  and services still ship with specs (section 7).
- Cucumber HTML report: `target/cucumber-reports/Cucumber.html`.
- Playwright HTML report: `npm run e2e:report` (`target/playwright/report`).
- JUnit XML for CI/Sonar: `target/surefire-reports/`, `target/failsafe-reports/`,
  `target/test-results/TESTS-results-vitest.xml`. Sonar is configured
  (`sonar-project.properties`) but no server is assumed — do not run it per ticket.

## 7. Conventions tests must follow

**Naming decides which runner picks a Java test up** — get it wrong and the test silently never runs:

- `*Test.java` → unit test, Surefire (`test` phase). No Spring context; plain JUnit 5 + Mockito.
- `*IT.java` (or `*IntTest.java`) → integration test, Failsafe (`verify` phase). Annotate the
  class with `@IntegrationTest` (never a raw `@SpringBootTest` — the meta-annotation wires the
  test security config, synchronous async executor, and embedded SQL, and lets Spring reuse one
  cached context across ITs).
- Frontend: `<name>.spec.ts` next to `<name>.ts` / `<name>.vue`.
- Playwright: `*.spec.ts` under `src/test/javascript/playwright/`; tests that must run signed-out
  go in `anonymous.spec.ts` (the only file the `chromium-anonymous` project matches).

**Placement:** Java tests mirror the package of the class under test. Frontend specs are co-located.

**Style — follow the generated tests; they are the house style:**

- REST resources: `@AutoConfigureMockMvc` + `@WithMockUser`, mutate with `.with(csrf())`,
  `@Transactional` on the class, entity builders `createEntity()` / `createUpdatedEntity()`,
  and the `assertSameRepositoryCount` / `assertIncrementedRepositoryCount` helpers.
  Copy `TagResourceIT` as the template for a new entity resource.
- Entities: use `*TestSamples` for fixtures and `*Asserts` for field-by-field comparison;
  every entity has an `equalsVerifier` test via `TestUtil.equalsVerifier`.
- Assertions: AssertJ (`assertThat`), not JUnit `assertEquals`.
- Security in tests: OAuth2 is stubbed by `TestSecurityConfiguration` — never call a real Keycloak
  from a Java test.
- Vue: mount with `@vue/test-utils` `shallowMount`, stub HTTP with `sinon` stubs on `axios`
  (or `axios-mock-adapter`), stores with `createTestingPinia`. Vitest globals (`describe`, `it`,
  `expect`, `vi`) are available without import.
- Playwright: select by `data-cy` via `getByTestId(...)` (`testIdAttribute` is set to `data-cy`).
- `TechnicalStructureTest` (ArchUnit) enforces layering: `web` → `service` → `repository`/`domain`.
  New packages must respect it; do not relax the rule to make a ticket pass.

**Regenerated code:** entity CRUD tests are JHipster-generated from `ombuto.jdl`. If an entity
changes via the JDL, regenerate rather than hand-editing the generated tests; hand-written tests
for custom behaviour go in separate classes/specs so regeneration does not clobber them.

## 8. What NOT to test in the per-ticket TDD cycle

- **Playwright E2E.** Needs three running processes — Keycloak
  (`docker compose -f src/main/docker/keycloak.yml up -d`), backend (`./mvnw`, :8080) and Vite
  (`npm start`, :9000) — plus `E2E_USERNAME` / `E2E_PASSWORD` if not the defaults. Regression /
  dedicated E2E tickets only.
- **`-Pprod` Testcontainers runs and Cucumber features.** Need Docker and pull a PostgreSQL image.
  H2 (`testdev`) is the per-ticket database. Cucumber scenarios are only in scope for a ticket
  whose acceptance criteria name a `.feature` file.
- **The full backend `verify`.** Several minutes. Run only the ticket's own classes (section 3).
- **The full frontend run** (repo-wide ESLint + every Vitest spec, section 4). Regression closeout only.
- **Real OAuth2/Keycloak login flows, WebSocket end-to-end delivery across browsers, Docker image
  builds (`jib`), Sonar analysis, production webapp build (`npm run build`).**
- **Re-testing generated framework plumbing** (JHipster account/admin/health modules) that the
  ticket did not touch.

## 9. Known pitfalls on this project

- **Node 25+ breaks Vitest specs that touch `localStorage`** (`TypeError: localStorage.clear is
  not a function`). Node's built-in Web Storage global shadows happy-dom's. Run Vitest with
  `NODE_OPTIONS=--no-experimental-webstorage` (verified fix), or use Node 24 LTS. In PowerShell:
  `$env:NODE_OPTIONS='--no-experimental-webstorage'; npx vitest run <file>`.
- **`npm run lint` and `npm test` hang.** `eslint .` crawls `.ombutocode/` (Ombuto Code's own
  sources plus a 3.7 MB bundled `dist`), which `eslint.config.ts` does not ignore; it ran 20+
  minutes without finishing. With `--ignore-pattern ".ombutocode/"` the whole repo lints in ~9 s.
  Use the explicit commands in sections 4 and 5 until `.ombutocode/` is added to the `ignores` in
  `eslint.config.ts` (one-line fix, needs its own ticket); then remove this entry.
- **CRLF vs Prettier on Windows.** `.editorconfig`/Prettier expect LF, but with
  `core.autocrlf=true` regenerated files are checked out as CRLF, so `prettier --check` reports
  them as unformatted and `git status` lists ~170 files as modified although `git diff` is empty.
  This is line-ending noise, not a real change. `npx prettier --write <files>` on the ticket's own
  files fixes those files; do not mass-reformat the repo inside a ticket.
- **Avoid SQL reserved words as field/column names** (`value`, `order`, `key`, `user`, `rank`, …).
  PostgreSQL tolerates several that H2 rejects (`Syntax error in SQL statement … expected
  "identifier"`), so the failure only shows on the H2 (`testdev`) run and takes out every IT that
  joins the table. This happened with `Opportunity.value`, renamed to `valuerating` on 2026-09-18.
  Baseline after the rename: H2 → 124 + 445 tests green; `-Pprod` → 126 + 445 green.
- **`./mvnw test` does not run `*IT` classes.** A green `test` says nothing about REST/resource
  tests — use the `verify` command in section 3.
- **`CucumberTest` cannot pass under the default `dev` profile.** It runs in the unit (`test`)
  phase because of its name, and `CucumberTestContextConfiguration` has
  `@ActiveProfiles({ "test", "testprod" })`, which needs `DatabaseTestcontainer` — a class the `dev`
  profile excludes from compilation. Result: `ClassNotFoundException: …DatabaseTestcontainer`
  (or `Unresolved compilation problems` if an IDE compiled the class into `target/test-classes`).
  Use `-Pprod` with Docker running, or exclude it with the no-Docker command in section 4. This is generator
  behaviour, not a ticket regression. (The Failsafe `*CucumberIT*` exclude in `pom.xml` is a
  leftover and matches nothing.)
- **IDE and Maven share `target/`.** VS Code / Eclipse JDT compiles into `target/classes` and
  `target/test-classes` too, including files Maven's active profile excludes. Odd
  `Unresolved compilation problems` errors at test runtime (seen as unexplained `500`s in ITs)
  come from there, typically after renaming an entity field: the JPA metamodel (`Opportunity_`
  etc. in `target/generated-sources/annotations`) goes stale, the IDE compiles the `*QueryService`
  classes broken, and Maven treats them as up to date. Find them with
  `grep -rla "Unresolved compilation" target/classes target/test-classes`; recover with
  `rm -rf target/classes/com target/test-classes/com target/generated-sources target/maven-status`
  then `./mvnw -Dskip.installnodenpm -Dskip.npm compile` and re-run. Do not use `./mvnw clean` for
  this — it also deletes the dev database in `target/h2db/db`. A leftover broken
  `DatabaseTestcontainer.class` under the `dev` profile is harmless.
- **JUnit default timeout is 15 s per test** (`junit-platform.properties`). A test paused on a
  debugger breakpoint, or a genuinely slow IT, fails with a timeout rather than hanging.
- **Test logging is silenced** (`src/test/resources/logback.xml`, and `backend:unit:test` sets
  `-Dlogging.level.*=OFF`). When an IT fails with an unexplained `500`, re-run the single class
  via the raw `./mvnw` command in section 3 and raise levels in `logback.xml` locally (do not commit that).
- **H2 test database is file-based** at `target/h2db/testdb`. If ITs fail oddly after a Liquibase
  changelog edit, delete `target/h2db/` (or `npm run cleanup`) and re-run.
- **Do not run two Maven builds concurrently** in the same checkout — they share `target/` and the
  H2 file.
- **Spring context caching:** adding `@MockitoBean`, custom `properties`, or `@DirtiesContext` to an
  IT forces a fresh context (+10–20 s each). Prefer the shared `@IntegrationTest` setup.
- **Dev profile excludes `DatabaseTestcontainer.java` from test compilation.** IDE "cannot resolve"
  errors there under the default profile are expected.
- **Maven first run downloads the world.** Offline or cold caches: `npm run backend:build-cache` first.

## 10. Phase gates — what each agent runs

### Build phase (in_progress) — MUST run before finishing, CHANGED FILES ONLY

- Formatter (write):  `npx prettier --write <changed files>` — handles `.java`, `.ts`, `.vue`, `.json`, `.yml`, `.md`, `.scss`, `.html`
- Linter / vet:       frontend → `npx eslint <changed .ts/.vue files>`; backend → none — Checkstyle here only checks for `http://` URLs and cannot be file-scoped (left to the test phase)
- Type / compile check: backend → implicit: the section 3 Maven command compiles main + test sources first, a compile error fails it; frontend → none — `vue-tsc` not installed
- Tests written for this ticket: section 3 — `-Dtest=<Class>` for `*Test`, the `verify … -Dit.test=<Class>` form for `*IT`, `npx vitest run <spec>` for frontend

### Build phase — MUST NOT run (too slow, or owned by a later phase)

- Full test suite:    `npm run backend:unit:test -- -Pprod`, `npx vitest --run --coverage` (or `npm test`)
- Repo-wide lint:     `npx eslint .` / `npm run lint`, `npm run prettier:check`, `npm run backend:nohttp:test`, `npm run backend:doc:test`
- Integration / E2E:  `npm run e2e` (Playwright), anything with `-Pprod` (Testcontainers), `CucumberTest`
- Production build / packaging: `npm run build`, `npm run java:jar:prod`, `npm run java:docker`

### Test phase — runs regardless

- The ticket's tests (section 3) plus `npx prettier --check` and `npx eslint` on the ticket's files.
- Additionally, for backend tickets: existing `*IT` classes covering the changed resource/service
  (e.g. a change to `TagService` → `TagResourceIT`), `TechnicalStructureTest` when packages or
  cross-layer dependencies changed, and `npm run backend:nohttp:test` when URLs were added to any file.
- For tickets touching Liquibase changelogs or entities: at minimum the affected entity's
  `*ResourceIT`.

### Splitting the tests themselves

- **Build agent runs:** the `*Test` unit tests and `*.spec.ts` specs it wrote, existing unit
  tests/specs for the files it changed, and the single `*IT` class it wrote or directly changed
  (H2-backed, ~35 s — acceptable).
- **Test agent only:** other `*IT` classes touching the changed area, `TechnicalStructureTest`,
  Checkstyle/Javadoc checks. `CucumberTest` (`-Pprod`, Docker) and Playwright specs only when the
  ticket's acceptance criteria explicitly call for them and the environment is running.
- **Regression closeout ticket only:** `npm run backend:unit:test -- -Pprod` and the two frontend
  commands from section 4, in full. Without Docker, fall back to the no-Docker command in section 4 and record
  Cucumber as skipped with the reason. `npm run e2e` when Keycloak + backend + Vite are up —
  otherwise record it as skipped.

### Notes

- The Java compile cannot be scoped to individual files; it always compiles the module. Only
  errors in the ticket's own files count against the ticket.
- Frontend coverage is reported but not gated (section 6), so nothing mechanical catches untested
  frontend code — build agents must ship specs with new components/services, and the test agent
  checks that they exist.
- Pre-existing failures in untouched files are never the current ticket's responsibility, in
  either phase. Record them in the ticket notes and raise a separate ticket.
- See also section 8 — what to leave out of the per-ticket TDD cycle.
